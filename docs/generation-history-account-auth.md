# Account identity repair

The original history implementation confused an email app-session JWT with a pipeline identity JWT. A live email session was rejected by the history verifier. Earlier synthetic-token source acceptance does not prove this integration.

The frontend now calls the existing POST `/authUserCheck` (staging `/staging/authUserCheck`) with JSON `{sessionToken, identityToken?}`. The session token is the verified sign-in session; the optional identity token is fresh legacy proof obtained from the anonymous resolver, never a submitted owner ID. No Authorization header is required by this resolver contract. The backend owns signature verification and immutable account-to-identity association. It reuses an established account marker; first linkage may adopt only a proven unclaimed/same-account legacy identity, and foreign proof produces a distinct account identity without exposing foreign history.

The resolver returns `{user_id, identity_token, ...}`. The frontend retains the account credentials only in memory and refreshes them before signed-in pipeline calls, including retries/refinements. The backend caps their expiry at the app session expiry. History list/detail/delete send the email app session as JSON `sessionToken` and are sent only after account bootstrap succeeds. Pipeline requests send the scoped account (or signed-out anonymous) identity token as JSON `sessionToken`. Neither request sends Authorization; both use `credentials: omit`. Account bootstrap is unchanged. History never authenticates using the device token. Staging resolver, history and pipeline routes all use `/staging/` and require the backend's isolated collection bindings.

Sign-in/session rotation and sign-out invalidate pending account resolutions. Account changes also cancel an active generation. Late anonymous or account responses cannot replace the current account's identity. Bridge failure blocks signed-in generation/history rather than falling back to anonymous access. Anonymous generation keeps its existing resolver path; the backend must refuse anonymous capabilities for an identity already claimed by an account.

Evidence is synthetic and local: unit tests exercise real email-session-shaped request semantics, owner-field omission, delayed response rejection, logout, malformed responses and retry. Browser tests check email-vs-generation token separation, account A→B switching during a delayed bridge, and fail-closed behavior. Full-suite and independent-review results are recorded with the PR head. Backend source/emulator acceptance, deployment, CORS, real authenticated reads, two-account isolation and editor retest remain separate; no live writes or deployment are authorized by these tests. Preserve Stuart's manual backend workflow changes.

Body-token transition (owner authorized): backend may accept legacy headers but must reject conflicting body/header credentials. JSON Content-Type still triggers a preflight; removing Authorization reduces the requested headers to content-type with credentials omitted. A local cross-origin browser probe observed OPTIONS requesting only content-type and a successful POST with no Authorization/cookies. Production/staging invalid-token list probes returned readable401; these are not valid-session acceptance. The preview browser also allowed the Authorization negative control, so this harness does not establish strict browser CORS enforcement; deployed ordinary-browser acceptance remains required. No valid bootstrap, generation or deletion was performed.
